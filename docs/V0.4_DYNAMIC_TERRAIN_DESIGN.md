## 2. V0.4 地图改造方案

### 2.1 核心玩法：两种操作必须同时存在

| 操作 | 作用 | 经济 | 阶段 |
|---|---|---|---|
| **拆除废墟** | 打开横廊缺口，缩短/改变路线 | +20 金（沿用现值） | 仅准备阶段 |
| **建造防御墙** | 封堵直道，强制敌人绕行横廊或回到长路线 | -30 金（新参数） | 仅准备阶段 |

**为什么不能只靠拆废墟**：单纯拆废墟只会单调缩短路线（对防守方反而不利——敌人更快到核心），玩家缺乏主动塑造战场的动机。墙体提供"延长敌人行进 / 改变火力覆盖分布"的反向手段，两者组合才形成真正的**路线博弈**。

### 2.2 两种不同战术价值的路线改造方案

所有数字均由独立 A* 模拟脚本按 §4 规则（禁止斜向）计算，路线长度单位为格（=1 世界单位）。火力覆盖按"机枪塔射程 4.5、忽略高度、XZ 平面"统计路线经过格数。

#### 方案 A：拆双废墟 + 封左横廊 —— "上半场集中火力"（牺牲下半场，赌上半场输出）

- 操作：拆除 (6,7) 与 (11,7) 双废墟 + 建墙 (5,7)（封左横廊入口）。
- 结果路线（31 格）：入口 → 沿原路走到 (8,3) → 下到 (8,7) → **走右横廊** (9,7)…(12,7) → (13,7) → 原路到核心。
- **战术价值**：完全放弃下半场（平台 (6,12)(10,12)(17,10) 覆盖归零），把敌人全部集中到上半场与右横廊；适合玩家把资源集中在 (6,5)(15,3)(15,8) 一线、并主动放弃下方防区的打法。
- **反面教学**：若只拆 (6,7) 不拆 (11,7)，再封 (8,8)，则 (8,7) 往下被墙挡、右横廊又不通 → **不连通，会被连通性校验拒绝**。这正说明 §6 校验的必要性。

#### 方案 B：拆双废墟 + 封右横廊 —— "下半场拉长输出"（拉长路线，最大化输出时间）

- 操作：拆除 (6,7) 与 (11,7) 双废墟 + 建墙 (10,7)（封右横廊中段）。
- 结果路线（29 格）：入口 → (3,7) → **走左横廊** (4,7)…(7,7) → (8,7) → (8,8)(8,9)(8,10) → 下半场原路 → 核心。
- **战术价值**：比"全横廊直达"的 23 格拉长 6 格，恢复下半场 3 个平台的火力覆盖，同时上半场 (5,1)(10,1) 失效。适合以重炮 + 下方电磁塔为主、追求最大总伤害输出的打法。

#### 方案 C（对照）：全横廊直达 —— "极限近道"（高风险）

- 操作：只拆 (6,7) 与 (11,7)，不建墙。路线从 37 格压缩到 **23 格**（-38%）。
- 战术价值：路线最短、敌人最快到核心；虽然拿到 +40 金，但输出窗口大幅缩水，多数平台覆盖归零。**作为反面参照**，说明为何墙机制不可或缺。

#### 路线变化对照表

| 场景 | 路线长度 | 相对基线 | 覆盖为 0 的平台（机枪射程） | 经济 |
|---|---|---|---|---|
| S0 原始基线 | 37 | — | 无 | 0 |
| S1 只拆 (6,7) | 29 | -8 | (5,1)(10,1) | +20 |
| S2 拆双废墟（全横廊） | 23 | -14 | (5,1)(10,1)(6,12)(10,12) | +40 |
| S2a 双拆 + 墙(5,7) | 31 | -6 | (6,12)(10,12)(17,10) | +40-30=+10 |
| S2b 双拆 + 墙(10,7) | 29 | -8 | (5,1)(10,1) | +40-30=+10 |
| S2c 双拆 + 双墙(5,7)(12,7) | 37 | 0 | 无（回到原火力分布） | +40-60=-20 |

> 关键结论：**双墙 (5,7)+(12,7) 可让路线在"已改地形"下恢复原始 37 格火力分布**，同时在拆除环节拿到 +40 金——但净经济为 -20 金。这是"以经济换火力"的真实战术取舍，需在第 3 波验证是否划算（详见 §9）。

### 2.3 路线变化示例（S2a：双拆 + 墙封左廊，31 格）

```
阶段①初始： (0,7)→(1,7)→(2,7)→(3,7)→(3,6)…上绕…(8,7)→(8,8)…下绕…(18,7)→(19,7)   [37格]
阶段②拆(6,7)(11,7)：预判路线变 (0,7)…(3,7)→(4,7)(5,7)(6,7)(7,7)→(8,7)→(9,7)…(12,7)→(13,7)…→(19,7)  [23格]
阶段③墙封(5,7)：预判路线退回  (0,7)…(3,7)→(3,6)…(8,7)→(9,7)…(12,7)→(13,7)…→(19,7)  [31格]
预览同时显示：当前路线(蓝) + 预计路线(橙)，长度 37→31（-6），并高亮失效平台 (6,12)(10,12)(17,10)。
```

### 2.4 关于第三处废墟 (16,11)

该格不在横廊上，拆除后**不改变入口→核心最短路**（周围是障碍 (15,11)(16,9)(18,11) 与装饰地面）。V0.4 中它的定位是：

- **纯经济点**：+20 金，作为"练手"操作，让玩家熟悉拆除流程而不必担心破坏路线；
- 保留其"可拆 + 可通行"语义一致性，但不纳入 §1.5 横廊白名单（避免意外抄近路）。

## 4. 动态寻路数据结构

### 4.1 设计原则：四层分离

将当前"配置常量即真相"的单层结构拆为四个独立层，**视觉、通行、建造、经济互不耦合**：

```
TerrainGrid (纯数据，RefCounted)
 ├── cell_type      : Dictionary<Vector2i, int>   地形类型枚举（GROUND/ROAD/PAD/OBSTACLE/RUBBLE/WALL/ENTRY/CORE）
 ├── passable       : Dictionary<Vector2i, bool>  可通行性（由 cell_type 派生 + 动态覆盖）
 ├── buildable      : Dictionary<Vector2i, bool>  可建造性（墙体白名单 ∩ 当前无占用）
 └── wall_cost / wall_limit                       经济参数（配置文件）
VisualTerrain (Node3D)
 └── 仅负责把 TerrainGrid 渲染成体素模型；不参与寻路判定
PathManager (A* 适配器)
 └── 输入 TerrainGrid 快照 → 输出格子路径 / 世界坐标点
```

关键点：**寻路只读 `passable`，建墙只写 `cell_type=WALL` 并派生更新 `passable`，视觉层订阅变更事件**。三者不共享可变状态。

### 4.2 枚举与配置（新增到 `detour_config.gd`）

```gdscript
enum CellType { GROUND, ROAD, PAD, OBSTACLE, RUBBLE, WALL, ENTRY, CORE }

# 初始可通行白名单 = 原始路径 ∪ 横廊空格（不含废墟）
const DYNAMIC_PASSABLE_CELLS := [
    # 原始路径 38 格（展开）...
    # 横廊：(4,7)(5,7)(7,7)(9,7)(10,7)(12,7) —— 废墟格 (6,7)(11,7) 由 RUBBLE 单独控制
]
const TACTICAL_WALL_CELLS := [
    Vector2i(3,4), Vector2i(3,5), Vector2i(3,6),
    Vector2i(8,6), Vector2i(8,8), Vector2i(8,9),
    Vector2i(13,6), Vector2i(13,8), Vector2i(13,9), Vector2i(18,6),
]
const WALL_COST := 30
const WALL_LIMIT := 4
const RUBBLE_REWARD := 20   # 与现有 _try_clear_rubble 一致
const ASTAR_DIAGONAL := false
```

### 4.3 TerrainGrid 接口（新脚本 `scripts/terrain_grid.gd`）

```gdscript
extends RefCounted
class_name TerrainGrid

signal terrain_changed(cell: Vector2i)

var _cell_type: Dictionary = {}      # Vector2i -> CellType
var _walls: Dictionary = {}          # Vector2i -> true
var _cleared_rubble: Dictionary = {} # Vector2i -> true

func setup_from_config() -> void
func get_type(cell: Vector2i) -> int
func is_passable(cell: Vector2i) -> bool
func is_buildable_wall(cell: Vector2i) -> bool   # TACTICAL_WALL_CELLS ∩ 未占用 ∩ 非入口/核心/平台/障碍
func wall_count() -> int

func can_place_wall(cell: Vector2i) -> bool       # 只校验合法性，不改数据
func preview_wall(cell: Vector2i) -> TerrainGrid  # 返回副本，绝不改 this
func commit_wall(cell: Vector2i) -> bool          # 合法才写 this 并 emit
func can_clear_rubble(cell: Vector2i) -> bool
func preview_clear(cell: Vector2i) -> TerrainGrid
func commit_clear(cell: Vector2i) -> bool
func duplicate() -> TerrainGrid                   # 深拷贝，供预览隔离
```

**预览隔离强制约定**：`preview_*` 一律 `duplicate()` 出新 grid 再改；正式地图、`PathManager` 路线、`gold` 在预览阶段**只读**。确认后才调用 `commit_*` + 扣金币 + 更新正式路线与模型。

## 5. 系统接口设计

### 5.1 PathManager 扩展（保留现有接口，新增动态接口）

现有 `rebuild()/get_points()/get_point()/point_count()/total_length()/progress_at()` **全部保留**，V0.4 不改变其对外语义。新增：

```gdscript
# 用给定网格快照计算路线（格子序列 + 世界点）
func compute_route(grid: TerrainGrid,
                   start: Vector2i = Vector2i(0,7),
                   goal:  Vector2i = Vector2i(19,7)) -> Array[Vector2i]

# 把格子序列转成世界坐标点（复用 grid_to_world，y = ROAD_Y + 0.30）
func cells_to_world(cells: Array) -> Array[Vector3]

# 连通性 + 合法性校验：建墙确认前必须通过
func would_remain_connected(grid: TerrainGrid, wall_cell: Vector2i) -> bool

# 攻击后应用：仅准备阶段调用；重建 world_points 并 emit path_changed
func apply_grid(grid: TerrainGrid) -> void
```

`compute_dynamic_path()`（现有预留函数）**重构为内部调用 `compute_route`**，并补齐：

- `astar.set_point_solid(cell, true)` 覆盖所有 `not grid.is_passable(cell)` 的格子；
- `astar.diagonal_mode = AStarGrid2D.DIAGONAL_MODE_NEVER`（**禁止斜穿墙体和障碍拐角**，与预留代码一致）；
- 返回格子序列后统一转世界点。

### 5.2 与现有代码的衔接

| 关注点 | 处理方式 |
|---|---|
| 敌人行进 | `detour_enemy.gd` 继续读 `path_manager.get_points()`；V0.4 **不使用战斗中重算路径** |
| 进度/索敌 | `progress_at()` 基于新 `world_points` 重算；炮塔索敌读的 `progress` 自动正确 |
| 波次准备阶段检测 | `main.wave_active == false && !game_over && wave_index < WAVES.size()` |
| 状态隔离 | 预览期 `PathManager` 不 `apply_grid`（正式路线不动）；确认后才 apply |

## 6. 拆除、建造、预览、确认的完整状态流程

```
                ┌──────────────── IDLE（无改造模式）────────────────┐
                │  点击废墟 → 预览拆；点击 W 键/地形按钮 → 进入建墙模式 │
                ▼                                                   │
          PREVIEW（临时状态）                                         │
   grid_preview = grid.duplicate() + 拟议操作                         │
   route_preview = path_manager.compute_route(grid_preview)           │
   ├─ 不连通 / 非法 → 显示红色禁止提示，不允许确认                      │
   └─ 合法 → 同时绘制：当前路线(蓝) + 预计路线(橙)                      │
             显示：长度 37→31（-6）、失效/新增覆盖平台、金币变化         │
                │                                                   │
       鼠标移动/改选 → 重算 PREVIEW（不改正式数据）                     │
       左键确认 ──► 检查：准备阶段? 金币够? 墙数<上限? 仍连通?           │
                │     ├─ 否 → toast 反馈，留 PREVIEW                  │
                │     └─ 是 → COMMIT                                  │
       ESC/右键 ────────────────────────────────────────────────────┘（取消回 IDLE）

COMMIT（仅此处产生副作用，顺序固定）：
  1) gold += (拆? +20 : -30)
  2) grid.commit_wall() 或 grid.commit_clear()
  3) path_manager.apply_grid(grid) → path_changed
  4) VisualTerrain 更新对应格子模型（旧废墟/新墙）
  5) main._refresh_hud() + toast
  6) 回 IDLE
```

**战斗中的约束**：`wave_active == true` 时进入 PREVIEW 会提示"仅准备阶段可改造"并拒绝；已存活敌人不重新寻路，路线变更只对下一波生效（第一版明确不处理战斗中重寻路）。

## 9. 潜在的策略单一化问题与解决建议

### 9.1 风险

1. **"最短路线"陷阱**：拆双废墟把路线压到 23 格，敌人最快到核心。若 +40 金不足以弥补输出窗口缩水，最优解会退化为"不改造"，地形系统形同虚设。
2. **"双墙回原始"最优解**：§2.2 的 S2c 能在拿 +40 金的同时把火力分布恢复原样（净 -20 金）。若实测划算，所有玩家都会固定这一套，策略单一。
3. **纯近道流/纯龟缩流**：只拆不建 or 只建不拆，都可能让某类塔（机枪/重炮/电磁）彻底失效，降低可玩性。
4. **墙位固定**：10 个候选墙位中若只有 2–3 个真正有效，选择空间仍然狭窄。

### 9.2 解决建议（V0.4 实现阶段评估，当前不改数值）

| 建议 | 说明 |
|---|---|
| **波次差异化目标** | 第 2 波设"护送/限时"目标，鼓励拉长路线；第 3 波设"资源"目标，鼓励近道取金，形成节奏变化 |
| **墙体造价递增** | 每多建一块墙 +10 金（30/40/50/60），抑制"无脑双墙回原始" |
| **横廊分段可拆** | 把 (6,7)、(11,7) 各拆成 2 个半格废墟（+10/+10），允许部分打开，增加粒度 |
| **覆盖可视化反制** | 预览强制显示"失效平台清单"与预计 DPS 变化，让玩家直观看到近道的代价（已在 §6 流程中） |
| **敌人类型适配** | 重装机甲（慢、高血）适合拉长路线用电磁持续减速；侦察虫（快、低血）适合近道用机枪拦截——用敌人组合引导路线选择 |
| **-delay 启用右延伸段** | (14,7)–(17,7) 暂不开放；若后期证明路线选择不足，再作为 V0.4.1 内容加入 |

### 9.3 与"策略偏弱"遗留问题的关系

纯重炮 / 纯电磁偏弱的问题**不在本轮调整范围**。地形改造完成后，路线可被拉长或集中，会直接改变这两种塔的有效输出窗口（重炮吃"路线集中+经过爆炸区次数"，电磁吃"拉长路线+减速叠加"）。建议在 V0.4 实装并用 §9.2 机制跑通后，再统一评估是否需要数值调整。
